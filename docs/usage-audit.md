# Jobsieve usage audit

September 19, 2026. Scope: the deployed Next.js application's ingestion, database queries, scheduled work, manual refresh, authentication persistence, and notification delivery. Neon Launch was confirmed through Vercel's resource API. No billing or compute settings were changed.

## Findings and fixes

| Finding                                                                     | Fix                                                                                                    | Regression evidence                                                                              |
| --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------ |
| Job lists fetched full descriptions that cards never display                | Return summary columns; keep descriptions on detail requests                                           | List response stays below 5 KB with 112 KB descriptions; detail retains original content         |
| Alert delivery fetched a description for each recipient/channel/retry       | Recheck current eligibility in SQL and return only notification fields                                 | Delivery response stays below 5 KB; settings, age, consent, role, score and ownership cases pass |
| Manual sync refetched ranked jobs after every source batch                  | Invalidate the list once when sync completes                                                           | Browser test observes one final refetch across three batches                                     |
| Every feed refresh rewrote every existing job, including large descriptions | Skip unchanged row updates; refresh last-seen hourly and update changed content immediately            | PostgreSQL row versions remain unchanged across repeated and concurrent refreshes                |
| Each authenticated request rewrote the user even when email was unchanged   | Read existing users; update email only when changed                                                    | Row-version tests also preserve profile and verified-email behavior                              |
| Frequent, staggered background work kept compute awake                      | Align source polling at 15-minute boundaries and run notifications two minutes later                   | Schedule coverage and invocation-budget test; 4,780 to 1,324 daily scheduled calls               |
| Failed sources could be repeatedly retried sooner than normal polling       | Keep their normal source cooldown; successful polls anchor cooldown to the start with scheduling grace | Failure, partial failure and successful cooldown tests                                           |
| Any user's manual sync scanned every account for alerts                     | Restrict manual scans to the authenticated account                                                     | Two-user test; cron still scans all enabled accounts                                             |
| Notification scans could overlap across cron invocations                    | Shared five-minute gate, longer than the route's four-minute lifetime                                  | Concurrent acquisition test                                                                      |
| Repeated crashes could bypass the five-attempt delivery limit               | Count expired leases toward the limit and fail exhausted deliveries                                    | Five consecutive crash-recovery claims stop and the next delivery proceeds                       |
| Reducing worker frequency would also reduce delivery capacity               | Raise the batch cap to 200 and stop claiming after two minutes                                         | Backlog-cap and deadline tests; current delivery completes before stopping                       |
| HTTP abort alone did not impose a database execution limit                  | Set a 15-second PostgreSQL statement timeout in each Neon HTTP transaction                             | Driver-boundary test, production request verification                                            |
| Ranked list queries evaluated the score in both projection and filtering    | Materialize the score once, then apply the score threshold                                             | SQL/JavaScript scoring and filtering parity suite                                                |

Review also found and fixed two concurrent-upsert edge cases introduced by suppressing unchanged writes: a first-insert conflict could be invisible to the statement snapshot, and a retitled source identity could return an unrelated job. Both have dedicated PostgreSQL regression tests.

## Operating limits

After this audit, the user requested daily scheduling. Sources now run at 00:00 UTC and the alert worker at 00:05 UTC, for 17 scheduled calls daily. Discovery may take up to 24 hours; jobs beyond the configured freshness window will not trigger alerts. The 15-minute schedules and invocation counts in the findings table describe the earlier audit deployment. Sources can report jobs late, provider failures can delay retries, and large alert backlogs can exceed that interval. The 200-delivery cap is per worker run, not a delivery guarantee.

These changes remove the identified amplification paths, not all ongoing usage. SQL still evaluates each user's criteria against candidate jobs. New jobs, accounts, saved application records and notification history accumulate in storage; this audit does not delete user history. Neon autoscaling, live traffic, provider latency and retained change history determine the actual bill. Measure a full healthy day's CU-hours and egress after rollout; the earlier quota-blocked sample is not a reliable cost baseline. Provider spending notifications remain a separate operational control, not a hard application budget.
